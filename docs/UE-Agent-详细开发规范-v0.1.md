## 2. 项目背景

长护险业务进入不同城市和行政区时，需要综合评估政策准入、潜在客户规模、站点触达范围、人员配置、服务产能、收入、成本和资金回收周期。

当前信息分散在调研报告、政策文件、业务经验和 Excel 测算模型中，存在以下问题：

- 同一指标可能存在官方值、历史值、推算值和人工判断值。
- 公开数据有时滞和统计口径差异，不能直接作为最终输入。
- Excel 中的字段、单位和公式缺少统一版本管理。
- 计算结论难以追溯到具体来源和参数版本。
- 城市、区县和单站点的市场规模容易混用。
- 多人协作时，无法确定谁在什么时间修改了什么参数。

UE Agent 的目标是把这些信息整理为可复算、可追溯、可审核的业务决策系统。

## 3. 产品定位

产品名称：UE Agent。

产品定位：长护险城市与单站投资决策工作台。

首版核心问题：在一个已选定城市和行政区内，按照给定政策、市场和运营条件，测算一个护理站从筹备到平台期的客户规模、人员需求、利润和现金流表现。

### 3.1 产品目标

1. 建立统一的城市、政策、市场和成本参数库。
2. 将现有 Excel 模型转为版本化的确定性计算引擎。
3. 输出可解释的 24 个月经营与现金流结果。
4. 为每个参考数据保存来源、日期、适用区域和可信度。
5. 支持业务人员显式覆盖参考值，并保留修改记录。
6. 为后续政策检索、爬虫更新和多城市比较预留结构。

### 3.2 首版非目标

- 不自动替代管理层作出最终投资决策。
- 不自动提交长护险定点机构申报。
- 不管理老人服务订单、护理排班和实际履约。
- 不自动生成或伪造业务回访记录。
- 不在首版实现全国所有城市的实时政策覆盖。
- 不在首版引入复杂地图路径优化。

## 4. 用户角色与权限

| 角色 | 主要职责 | 主要权限 |
|---|---|---|
| 业务人员 | 新建项目、填写参数、运行测算 | 项目编辑、参考值选择、测算运行、结果查看 |
| 城市负责人 | 确认本地政策和经营假设 | 本城市数据审核、场景审批、结果确认 |
| 政策运营 | 维护政策、申报材料和公开数据 | 政策入库、来源审核、数据有效性管理 |
| 模型管理员 | 管理参数定义和公式版本 | 发布模型版本、维护参数范围、查看回归测试 |
| 管理层 | 查看结论和比较结果 | 只读查看已确认测算和摘要报告 |
| 系统管理员 | 用户、权限、任务和系统配置 | 全局管理，不直接修改已发布计算结果 |

权限采用基于角色的访问控制。数据修改权限与模型发布权限分离，避免业务输入修改者直接改动核心公式。

## 5. 整体功能架构

### 5.1 项目管理

功能：

- 新建、复制、归档测算项目。
- 选择省、市、区县和站点。
- 绑定模型版本和政策版本。
- 保存草稿、提交确认、查看历史结果。
- 显示数据完整度、风险状态和最近更新时间。

每个项目可包含多个测算场景，例如基准、乐观、悲观或自定义场景。场景之间复制后独立保存。

### 5.2 U1 单站 UE 测算

U1 是首版唯一要求完整闭环的业务模块，包含：

1. 城市与政策选择。
2. 市场规模输入。
3. 站点空间与触达输入。
4. 人员、服务和效率输入。
5. 收入、成本和风险输入。
6. 参数复核。
7. 运行测算。
8. 结果解释和快照保存。

### 5.3 城市与市场资料

保存以下内容：

- 城市和区县基础信息。
- 常住人口、年龄结构和人口密度。
- 职工医保、居民医保参保人数。
- 失能率和居家护理比例。
- 居民收入、养老消费和护理员工资。
- 已有站点、计划站点和竞争信息。
- 数据来源、发布日期、统计期和可信度。

### 5.4 长护险政策中心

支持按省、市、区县和有效日期检索：

- 政策文件及历史版本。
- 覆盖人群和待遇标准。
- 服务项目、服务时长和支付上限。
- 基金支付比例和个人支付比例。
- 定点机构准入条件。
- 申报材料清单。
- 人员数量和资质要求。
- 场地、设备、信息系统和上墙要求。

### 5.5 多城市对比

首版只保留数据结构和入口，不完成完整比较功能。后续比较维度包括：

- 政策是否落地。
- 覆盖人群。
- 服务单价和支付比例。
- 站点最低配置。
- 区域潜在客户规模。
- 初始投入、最大资金缺口和回收期。
- 数据完整度和可信度。

### 5.6 后台管理

包含：

- 用户与角色管理。
- 参数定义管理。
- 模型版本管理。
- 政策文档管理。
- 数据来源管理。
- 爬虫任务管理。
- 数据审核队列。
- 审计日志。

## 6. 系统架构

采用 Next.js + FastAPI 的模块化架构，首期按模块化单体部署。

```text
浏览器
  |
  v
Next.js Web
  |-- 项目管理
  |-- U1 测算界面
  |-- 城市资料
  |-- 政策中心
  |-- 后台管理
  |
  v
FastAPI
  |-- 项目与场景服务
  |-- 参考数据服务
  |-- 政策服务
  |-- 计算引擎
  |-- 审核与审计服务
  |
  +--------> PostgreSQL
  |
  +--------> Redis / Celery
                 |
                 +--> 公开数据采集 Worker
                 +--> 政策解析 Worker
                 +--> 定时刷新任务
```

### 6.1 架构原则

- 计算引擎与页面展示分离。
- 参考数据与业务确认值分离。
- 原始政策文件与结构化政策字段分离。
- 模型定义与计算结果分离。
- 爬虫采集与人工发布分离。
- 每个正式计算结果必须绑定不可变的模型版本和输入快照。

| status | 启用状态 |

#### StationProject

| 字段 | 含义 |

| id | 项目唯一标识 |
| name | 项目名称 |
| region_id | 所在行政区 |
| address | 站点位置 |
| station_mode | 自营、收购、联营 |
| status | 草稿、评审中、已确认、已归档 |
| owner_id | 项目负责人 |
| created_at | 创建时间 |

### 8.2 政策资料

#### PolicyDocument

| 字段 | 含义 |
|---|---|
| id | 政策文件唯一标识 |
| title | 标题 |
| document_no | 文号 |
| issuer | 发布机关 |
| region_id | 适用区域 |
| published_at | 发布日期 |
| effective_from | 生效日期 |
| effective_to | 失效日期 |
| status | 草稿、待审核、有效、失效 |
| source_url | 官方来源链接 |
| file_hash | 文件指纹 |

#### PolicyRequirement

保存政策中的结构化规则：覆盖人群、服务方式、小时单价、月度上限、基金比例、人员要求、面积要求、材料要求等。每条规则必须关联政策文件、原文位置和适用日期。

### 8.3 参考数据

#### ReferenceDatum

| 字段 | 含义 |
|---|---|
| id | 参考数据唯一标识 |
| field_key | 标准字段编号 |
| region_id | 适用区域 |
| value | 数值或文本值 |
| unit | 单位 |
| period | 数据统计期 |
| source_id | 来源 |
| source_tier | 来源层级 |
| confidence | 可信度 |
| review_status | 待审核、已确认、已驳回 |
| valid_from/to | 有效期 |

来源层级固定为：

1. A：当前有效的官方精确数据。
2. B：官方历史数据或上级区域数据。
3. C：内部核实数据或明确公式推算数据。
4. D：行业参考、招聘信息或其他估算。

来源层级表示数据依据，不等同于业务重要性。

### 8.4 模型与场景

#### ModelVersion

记录模型版本号、发布时间、公式摘要、参数定义版本、测试状态和发布人。已发布版本不可原地修改，任何公式变化都创建新版本。

#### Scenario

记录项目、场景名称、模型版本、政策版本、状态和复制来源。

#### ScenarioInput

每条输入记录以下信息：

- 参数编号。
- 使用值。
- 单位。
- 值来源：参考值、人工填写、公式计算。
- 关联参考数据。
- 修改人和修改时间。
- 修改原因。

#### CalculationRun

每次运行记录输入快照、模型版本、运行状态、错误信息、开始结束时间和结果摘要。成功结果不可覆盖，只能产生新运行记录。

#### MonthlyProjection

按月份保存阶段、客户数、服务量、收入、成本、利润、现金流和人员需求。金额保存到最小货币单位或使用定点小数，禁止使用二进制浮点直接累计财务值。

## 9. U1 计算模型规范

### 9.1 计算原则

- 核心财务计算必须确定、可复现、可测试。
- 大模型不得直接生成核心财务数值。
- 所有公式使用标准参数编号，不直接引用页面位置或 Excel 单元格。
- 每个参数必须定义名称、单位、范围、是否必填和来源类型。
- 缺失值不得自动按零处理。
- 真正的零、空缺、不适用和无法计算必须分别表示。
- 金额统一使用人民币元，比例在存储层使用 0 到 1。
- 月份统一从 M0 或 M1 开始，初始投入发生时间必须明确。

### 9.2 四层测算结构

#### 第一层：政策可保障市场

分别计算职工和居民市场：

```text
职工潜在居家客户 = 职工医保参保人数 × 职工重度失能率 × 职工政策覆盖系数 × 居家护理比例
居民潜在居家客户 = 居民医保参保人数 × 居民重度失能率 × 居民政策覆盖系数 × 居家护理比例
区域政策客户池 = 职工潜在居家客户 + 居民潜在居家客户
```

如果当地政策尚未覆盖居民医保，居民政策覆盖系数为 0，并在结果中明确显示“居民端尚未纳入”，不使用推算值替代已落地市场。

#### 第二层：单站地理触达市场

```text
覆盖面积 = π × 覆盖半径²
覆盖人口 = 覆盖面积 × 区域人口密度 × 可达修正系数
微观失能客户池 = 覆盖人口 × 老龄人口比例 × 加权失能率 × 居家护理比例
单站可触达客户池 = MIN(区域政策客户池 × 区域覆盖占比, 微观失能客户池)
```

如业务已经取得医保部门提供的精确区级服务人数，应直接作为高优先级参考数据进入单站触达模型，并保留人工确认过程。

#### 第三层：站点运营能力

```text
单护理员月有效工时 = 日工作时长 × 月工作天数 × 目标利用率
单客户月服务工时 = 单次服务时长 × 月服务次数
单护理员理论服务客户数 = 单护理员月有效工时 ÷ 单客户月服务工时
所需护理员数 = MAX(政策最低人数, 向上取整(在服务客户数 ÷ 单护理员理论服务客户数))
```

平均通勤时长在首版通过“可达修正系数”体现。后续再引入道路网络和路径优化。

#### 第四层：财务与现金流

```text
长护险服务收入 = 在服务客户数 × 单客户月服务工时 × 服务单价
基金应收 = 长护险服务收入 × 基金支付比例
个人应收 = 长护险服务收入 × 个人支付比例
可确认收入 = 基金应收 × (1 - 结算扣减率) + 个人应收 × (1 - 坏账率) + 辅助收入
月净利润 = 可确认收入 - 月变动成本 - 月固定成本 - 当月损益费用
累计现金流 = 上月累计现金流 + 当月实际回款 - 当月现金支出
```

装修、设备和一次性物料的现金支出在 M0 进入现金流；如需计入利润表，则按确认的折旧或摊销周期进入月度损益，禁止在 M0 和月度现金支出中重复扣减。应收回款周期影响现金流，不改变收入确认口径。首版按月度近似处理，后续如有实际账期数据再细化到日。

### 9.3 客户爬坡

首版默认采用线性爬坡：筹备期客户为 0，启动期从 0 增长到平台期目标客户数，平台期按照流失和补充客户保持稳态。

平台期目标客户数：

```text
平台期目标客户数 = 单站可触达客户池 × 目标市场渗透率
```

该结果不能超过站点在当前人员方案下的运营能力。系统需要同时展示“市场约束”和“产能约束”中哪一个成为瓶颈。

### 9.4 核心输出

| 指标 | 定义 |
|---|---|
| 初始投资 | M0 发生的装修、设备、预付和启动周转金现金支出 |
| 月度盈亏平衡月份 | 第一个月净利润大于或等于 0 的月份 |
| 累计现金流回正月份 | 第一个累计现金流大于或等于 0 的月份 |
| 投资回收期 | 从 M0 到累计现金流首次回正的月数 |
| 最大资金缺口 | 全测算周期内累计现金流的最低值绝对额 |
| 平台期月均收入 | 平台期总收入除以平台期月份数 |
| 平台期月均净利润 | 平台期净利润总和除以平台期月份数 |
| 平台期净利率 | 平台期净利润总和除以平台期收入总和 |
| 24个月累计净利润 | M1 至 M24 月净利润之和 |
| 24个月期末累计现金流 | M24 的累计现金流余额 |
| 盈亏平衡客户数 | 覆盖固定成本和单位变动成本所需的最小在服务客户数 |

“投资回收期”和“月度盈亏平衡月份”是不同指标，不得引用同一结果代替。

### 9.5 模型版本与发布

模型状态包括：草稿、验证中、已发布、已停用。

发布模型版本前必须：

1. 通过参数完整性检查。
2. 通过公式单元测试。
3. 通过边界值测试。
4. 使用至少三个城市或场景完成回归测试。
5. 与经业务确认的 Excel 基准结果核对。
6. 记录与上一版本的变化。

## 10. 现有 Excel 模型迁移规则

现有工作簿可作为字段和页面结构参考，但不能直接作为生产计算服务。

迁移步骤：

1. 建立 Excel 单元格到标准参数编号的映射。
2. 列出全部公式和依赖关系。
3. 修正字段名称、单位和公式引用问题。
4. 确认初始投资、收入确认、回款和成本口径。
5. 形成三组人工验算案例。
6. 将确认后的公式实现为纯 Python 计算函数。
7. 以 Excel 结果作为测试样本，不在运行时调用 Excel。

当前已识别的迁移阻断项：

- “护理员日工作时段”字段与其现有公式含义不一致。
- 站点覆盖客户公式存在错误单元格引用，导致客户规模数量级异常。
- 累计净利润和累计现金流被再次求和。
- 现金流回正月份采用最大月份而非首次回正月份。
- 职工与居民医保市场口径和调研报告不一致。
- 初始投资包含范围需要按现金流口径重新确认。
- “启动期总亏损”等指标名称与现有公式含义不一致。

这些问题必须在模型基准版本发布前解决。

## 11. 公开数据采集规范

### 11.1 数据源范围

优先采集：

- 国家医保局及地方医保局。
- 省、市、区县人民政府网站。
- 统计局统计公报。
- 民政局、人社局、卫健委公开文件。
- 官方政策附件和政府信息公开栏目。

招聘网站、新闻媒体和行业报告只能作为低层级参考来源。

### 11.2 更新频率

- 常规来源每 2 至 3 天检查一次。
- 已知政策征求意见或申报窗口期可临时提高频率。
- 抓取任务只生成候选数据或变更提醒，不直接发布到参考值库。

### 11.3 抓取流程

```text
发现链接 -> 下载原始内容 -> 计算文件指纹 -> 解析元数据 -> 提取候选字段 -> 差异检测 -> 人工审核 -> 发布参考值
```

### 11.4 采集要求

- 保存原始 URL、抓取时间、HTTP 状态和内容指纹。
- 保存文件标题、文号、发布机关、发布日期和有效期。
- 同一 URL 内容变化时创建新版本，不覆盖原记录。
- 解析失败、字段缺失和内容变化必须进入审核队列。
- 遵守网站 robots、访问频率和公开信息使用要求。
- 不绕过登录、验证码或其他访问控制。

## 12. 政策检索规范

首版优先做结构化检索，不以聊天机器人作为主入口。

用户可按以下条件筛选：

- 省、市、区县。
- 政策状态。
- 发布机关。
- 发布时间和生效时间。
- 服务模式。
- 申报材料、人员要求、支付标准等主题。

搜索结果必须显示：标题、文号、适用区域、发布时间、生效状态、来源和最近核验时间。

政策详情页中的结构化结论必须能够定位到原文段落或附件页码。AI 提取结果在人工审核前标记为“机器提取，未确认”。

## 13. API 规范

### 13.1 基础约定

- 前缀：`/api/v1`。
- 数据格式：JSON，UTF-8。
- 时间格式：ISO 8601，服务端统一保存 UTC，页面按 Asia/Shanghai 展示。
- 金额：字符串形式的定点小数或最小货币单位整数。
- 分页：`page`、`page_size`，返回 `total`。
- 请求必须带追踪编号，响应返回 `request_id`。

### 13.2 主要资源

```text
GET    /api/v1/regions
GET    /api/v1/reference-data
GET    /api/v1/policies
GET    /api/v1/policies/{id}
POST   /api/v1/projects
GET    /api/v1/projects/{id}
POST   /api/v1/projects/{id}/scenarios
PATCH  /api/v1/scenarios/{id}/inputs
POST   /api/v1/scenarios/{id}/calculate
GET    /api/v1/calculation-runs/{id}
GET    /api/v1/model-versions
POST   /api/v1/crawl-jobs
GET    /api/v1/crawl-jobs/{id}
POST   /api/v1/review-items/{id}/approve
```

### 13.3 错误结构

```json
{
  "error": {
    "code": "SCENARIO_INPUT_INVALID",
    "message": "目标市场渗透率必须在 0 到 1 之间",
    "field": "target_penetration_rate",
    "request_id": "..."
  }
}
```

业务错误使用稳定错误码。页面不得通过解析中文错误文案判断逻辑。

## 15. 状态与错误处理

### 15.1 场景状态

- 草稿：输入可以修改。
- 待计算：输入已变化，旧结果失效。
- 计算中：禁止重复触发同一场景。
- 计算失败：保留错误编号和输入快照。
- 已计算：存在成功结果，但尚未业务确认。
- 已确认：负责人确认结果，输入和结果只读。
- 已归档：只读保存。

### 15.2 数据异常

- 必填输入缺失：阻止计算并定位字段。
- 单位不一致：阻止计算。
- 数值越界：阻止计算或要求填写原因。
- 参考数据过期：允许继续，但必须明确提醒。
- 来源可信度低：允许继续，并计入结果风险摘要。
- 爬虫失败：保留上次已发布值，不把失败解释为零。

## 16. 安全与合规

- 生产密钥仅通过环境变量或密钥管理服务提供。
- GitHub 仓库禁止提交真实密钥、Cookie、身份证号、手机号和老人个人资料。
- UE Agent 首版只处理城市、政策、站点和汇总经营数据，不接入老人个人明细。
- 如后续确需处理个人信息，必须单独进行权限、加密、脱敏、留存期限和本地化处理设计。
- 所有参数修改、政策发布、模型发布和结果确认写入审计日志。
- 公开仓库只保存代码、匿名测试数据和公开政策链接。

## 17. 测试规范

### 17.1 后端测试

- 参数校验单元测试。
- 每条核心公式单元测试。
- 缺失值、零值、负值和极端值测试。
- 模型版本回归测试。
- API 权限和状态流转测试。
- 数据库迁移测试。

### 17.2 前端测试

- 表单校验和单位显示。
- 参考值一键填入。
- 输入变化后旧结果失效。
- 图表和表格在空数据、长文本和大数字下的显示。
- 关键流程端到端测试。

### 17.3 模型基准测试

至少准备三个固定场景：

1. 已落地长护险、职工端为主的城市。
2. 已落地但市场规模较小的行政区。
3. 长护险尚未落地、仅做潜在市场准备的城市。

每个场景保存输入、预期月度结果和核心指标。模型公式变化后必须自动回归。

## 18. 代码质量规范

- TypeScript 开启严格模式。
- Python 使用类型标注。
- 前后端类型以 OpenAPI 契约为准。
- 禁止在页面组件中重复实现财务公式。
- 禁止在数据库触发器中隐藏核心业务计算。
- 单个模块只负责一个明确业务领域。
- 数据库变更必须通过迁移文件。
- 公共函数、公式和复杂判断必须有测试。
- 使用 Conventional Commits 格式记录提交。
- 合并前必须通过格式检查、类型检查、测试和构建。

## 22. V1 验收标准

V1 达到以下条件才视为可用：

1. 能创建一个城市、一个行政区、一个站点的测算项目。
2. 能区分参考值、人工值和公式值。
3. 能运行完整 24 个月模型。
4. 能正确输出首次月度盈亏平衡和首次累计现金流回正月份。
5. 能输出最大资金缺口、人员需求、盈亏平衡客户数和平台期指标。
6. 每个结果都能追溯到模型版本和输入快照。
7. 缺失数据不会被自动当作零。
8. 修改输入后旧结果会显示为失效。
9. 三个模型基准案例全部通过。
10. 页面不展示未经标识的低可信度或过期数据。

## 24. 评审重点

业务评审时重点确认以下内容：

1. 单站可触达客户池的计算方式是否符合实际选址逻辑。
2. 职工和居民市场在不同城市的启用条件。
3. 居家护理比例、失能率和市场渗透率的默认口径。
4. 单客户月服务次数与服务时长。
5. 护理员工资、计件、社保和最低配置的关系。
6. 初始投资和三个月周转金的包含范围。
7. 收入确认、医保回款周期和个人坏账口径。
8. 哪些结果需要负责人确认后才能提供给管理层。

以上评审结果形成模型基准版本后，再进入业务代码开发。
