# 组件与第三方代码复用规范

## 1. 目标

本规范解决两个问题：优先复用可靠资产，避免为了“复用”而继承无关业务和技术债。

## 2. 强制复用顺序

开发任何组件或页面前，必须按顺序检查：

1. `packages/ui` 是否已有满足需求的基础组件。
2. 是否可以组合已有基础组件和业务组件完成。
3. shadcn/ui 官方组件是否满足需求。
4. 技术白名单中的库是否已有对应能力。
5. 白名单参考项目是否有许可证明确且可隔离复用的实现。
6. 前五项均不满足时，才允许定制开发。

代码评审时必须能够回答：“为什么现有组件不能复用？”

## 3. 复用方式分级

| 方式 | 使用条件 | 要求 |
|---|---|---|
| 直接依赖 | 库稳定、职责单一、维护活跃 | 固定版本范围，记录许可证和用途 |
| 源码引入 | shadcn/ui 等代码归属项目的组件 | 保留来源，统一改为项目 token，补测试 |
| 局部移植 | 实现独立、许可证允许、移植成本低 | 只移植必要文件，删除原业务和无关依赖 |
| 模式参考 | 架构或交互有价值，但代码耦合高 | 重新实现，不复制源码 |
| 整仓二开 | 业务、架构和许可证均高度匹配 | 必须单独评审，当前 UE Agent 默认禁止 |

## 4. 技术白名单

除非写明架构决策记录，前端只允许使用以下基础方案：

| 类别 | 唯一选择 | 用途 |
|---|---|---|
| 应用框架 | Next.js 16 App Router | 页面、路由、服务端渲染和应用壳 |
| 基础组件 | shadcn/ui + Radix Primitives | 按钮、表单控件、弹窗、菜单等 |
| 样式系统 | Tailwind CSS v4 + CSS Variables | 布局、组件样式和语义 token |
| 组件变体 | class-variance-authority | 尺寸、状态和外观变体 |
| 类名工具 | clsx + tailwind-merge | 条件类名和冲突合并 |
| 图标 | `@tabler/icons-react` | 全站图标，统一线宽 1.75 |
| 表单 | TanStack Form + Zod | 表单状态、校验和类型约束 |
| 服务端状态 | TanStack Query | 请求、缓存和失效管理 |
| 数据表格 | TanStack Table | 排序、筛选、分页和列配置 |
| URL 状态 | nuqs | 筛选、分页和场景参数 URL 化 |
| 图表 | Recharts | 趋势、结构和对比图 |
| 日期 | date-fns | 日期计算和格式化 |
| 通知 | Sonner | 短暂操作反馈，不替代页面错误状态 |
| 测试 | Vitest + Testing Library + Playwright | 单元、组件和端到端测试 |

同类库不得并存。例如已经使用 TanStack Table，不得再引入 AG Grid；已经使用 Tabler Icons，不得混用 Lucide、Heroicons 或手写 SVG。

## 5. 组件层级

```text
packages/ui/src/
├── components/base/       # shadcn/Radix 基础组件
├── components/composite/  # 通用组合组件
├── components/domain/     # UE Agent 业务组件
├── icons/                 # Tabler 图标统一出口
├── styles/                # token、基础样式和通用工具
└── index.ts               # 公共导出
```

### 5.1 Base

只包含无业务语义的 Button、Input、Select、Dialog、Sheet、Tabs、Badge、Table、Tooltip 等。业务页面不得复制这些组件的实现。

### 5.2 Composite

包含 PageHeader、FilterBar、DataTable、MetricCard、FormField、EmptyState、ErrorPanel、ConfirmDialog、SourceBadge 等跨模块复用组件。

### 5.3 Domain

包含 ParameterInput、ReferenceValuePanel、CalculationStatus、ModelVersionBadge、SourceTracePanel、MonthlyProjectionTable 等 UE 业务组件。

Domain 组件可以依赖 Base 和 Composite，Base 组件不得反向依赖业务层。

## 7. 第三方代码准入

引入第三方代码前必须检查：

- 来源仓库和准确文件路径。
- 许可证是否允许当前用途。
- 最近维护时间、未解决安全问题和依赖风险。
- 是否引入新的状态管理、样式或组件体系。
- 是否能独立测试和替换。
- 是否包含遥测、外部 SaaS、密钥或用户数据上传。
- 是否符合本地优先和敏感数据要求。

许可证缺失、来源不明、依赖废弃或要求上传业务数据的代码不得引入。

## 8. 来源登记模板

每次源码移植在架构记录或提交说明中登记：

```text
来源项目：
来源链接：
原始许可证：
采用文件：
采用方式：直接依赖 / 源码引入 / 局部移植 / 模式参考
本地修改：
新增依赖：
安全检查：
替换或回退方式：
```

## 9. 禁止事项

- 不从无许可证仓库、随机博客或代码片段站直接复制代码。
- 不为一个页面引入新的 UI 库。
- 不把第三方组件原始颜色和圆角直接带入项目。
- 不保留未使用的演示数据、路由、环境变量和外部服务配置。
- 不因为“改起来快”复制一个现有组件形成 `Button2`、`NewTable` 或 `CustomDialog`。
- 不把完整第三方仓库的历史包袱视为有效复用率。
