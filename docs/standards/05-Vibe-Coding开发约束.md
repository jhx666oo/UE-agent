# Vibe Coding 开发约束

## 1. 目标

Vibe Coding 用于提高实现效率，不能替代架构、业务口径和验收。AI Agent 必须在受控上下文内工作，不得每次根据提示重新发明项目风格。

## 2. AI 开发前必读

开始任务前按顺序读取：

1. 根目录 `AGENTS.md`。
2. 当前目录最近的 `AGENTS.md` 或路径规则。
3. 与任务相关的 `docs/standards/` 文件。
4. 对应产品规范、模型规范和数据契约。
5. 当前模块已有代码、测试和最近修改。

没有读取现有模式前，不得生成新组件或新增依赖。

## 3. 每个任务的固定流程

### 3.1 理解

- 用一句话复述业务结果，不只复述页面名称。
- 明确用户角色、输入、输出、权限和失败情况。
- 明确哪些字段参与计算，哪些仅展示。
- 找到现有相似页面和组件。

### 3.2 复用判断

输出或记录：

```text
复用组件：
新增组件：
新增依赖：无 / 具体名称和理由
涉及 token：无 / 具体名称和理由
涉及业务口径：无 / 待确认事项
```

没有完成复用判断，不进入实现。

### 3.3 实现

- 先实现数据和状态边界，再实现视觉。
- 使用共享组件和语义 token。
- 一次只处理当前需求，不顺手重构无关模块。
- 文件职责单一；过大的组件拆为可测试单元。
- 不创建 `new`、`v2`、`final`、`temp` 命名的长期组件。

### 3.4 状态补齐

实现正常状态后，必须补齐 loading、empty、error、permission 和 stale 状态。表单还要覆盖未保存、校验失败和重复提交。

### 3.5 验证

按改动范围运行：

```text
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm test:a11y
pnpm build
pnpm test:e2e
```

页面改动必须检查桌面、平板和手机宽度。测算改动必须与 Excel 基准样例对照。

共享基础和组合组件达到 10 个，或开始开发第二个完整业务模块前，引入 Storybook 管理组件状态和视觉基线。首个 U1 页面阶段先使用 Playwright 固定截图，避免为尚未稳定的组件体系增加过早维护成本。

## 4. 仓库级指令策略

- `AGENTS.md` 保存跨工具、跨模块的核心规则。
- `.github/copilot-instructions.md` 只做 GitHub Copilot 入口。
- `.github/instructions/*.instructions.md` 使用 `applyTo` 限定目录。
- `.cursor/rules/*.mdc` 使用 glob 限定 Cursor 规则。
- 工具文件引用本规范，不复制数百行详细内容。

规则应短、明确、可执行。禁止“保持美观”“代码优雅”“用户体验好”等不可验收表述。

## 5. 前端生成硬约束

AI 不得：

- 在页面中直接实现 Button、Input、Dialog、Table 等基础组件。
- 引入 Ant Design、MUI、Chakra、Element、Naive UI 或第二套 UI 系统。
- 引入第二套图标、表格、表单、图表或日期库。
- 硬编码颜色、圆角、阴影和 z-index。
- 为单页增加全局 CSS。
- 使用 placeholder 代替表单标签。
- 只实现静态成功状态。
- 用随机渐变、玻璃拟态和动效填充空白。
- 使用虚构的业务数字冒充真实测算结果。

## 6. 业务与数据硬约束

AI 不得：

- 猜测缺失的长护险政策、服务单价或参保人数。
- 将公开数据直接标记为已确认值。
- 将缺失值转换为 0。
- 修改公式后只看页面结果，不补模型回归测试。
- 使用浮点数直接处理需要精确比较的金额。
- 在日志、测试快照或前端状态中暴露敏感个人信息。
- 让大模型成为核心测算链路的必要依赖。

业务口径不明确时，允许保留明确的阻断状态，不允许自行补全结论。

## 7. 依赖管理

新增依赖前必须：

1. 检查当前 `package.json` 或 Python 依赖。
2. 说明现有库为什么不能完成。
3. 检查许可证、维护情况和包体积。
4. 说明运行时依赖还是开发依赖。
5. 增加最小示例和测试。

禁止为了一个简单函数引入大型库。禁止在同一类别保留两个重叠依赖。

## 8. 文件和组件边界

- 页面文件负责路由组合，不承载大量业务计算。
- 计算规则放在后端计算引擎，不复制到多个 React 组件。
- API 类型从契约生成或共享，不手写互相漂移的重复类型。
- UI 基础组件放在 `packages/ui`。
- 业务模块放在明确的 feature 目录。
- 测试与被测模块靠近，端到端流程集中管理。

一个组件同时处理请求、计算、权限、表单和复杂展示时，必须拆分。

## 9. AI 输出自检

提交结果前，AI 必须回答：

- 是否复用了已有组件？
- 是否新增了任何颜色、依赖或全局样式？
- 是否覆盖所有必要状态？
- 是否保持参考值和确认值分离？
- 是否新增或修改了公式或业务假设？
- 运行了哪些验证，结果是什么？
- 有哪些未验证或需要业务确认的部分？

不得使用“应该可以”“理论上没问题”代替实际验证。

## 10. 推荐任务描述模板

```text
目标：说明用户最终要完成什么。
用户角色：说明谁使用。
范围：说明本次包含和不包含什么。
输入：字段、来源和单位。
输出：页面、数据和状态。
必须复用：指定现有组件或页面模式。
业务约束：明确不能猜测或覆盖的字段。
验收：列出可执行检查和关键场景。
```

AI 可以补充实现细节，不能擅自扩大范围或改变业务口径。
